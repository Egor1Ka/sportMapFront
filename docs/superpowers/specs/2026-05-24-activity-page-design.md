**Дата:** 2026-05-24

**Связанные специ:** `2026-05-17-playground-events-design.md` (события и check-ins — доменная модель)

## 1. Цель и контекст

Добавить отдельную страницу **`/activity`**, которая показывает «пульс города» в одном месте: карта с маркерами + лента карточек, в которой смешаны live check-ins, скоро стартующие события и топ-площадки рядом.

Сейчас события и check-ins живут только в контексте конкретной площадки (страница `/sports-map/[id]`). Discovery-сценария «куда пойти прямо сейчас» нет. Эта страница его закрывает.

### Сценарии, которые должны работать

1. **«Хочу куда-нибудь сейчас»** — пользователь открывает страницу, видит на карте красные пины с цифрами (где сейчас люди), листает ленту, кликает по интересному месту → попадает на страницу площадки.
2. **«Что планируется на вечер»** — синие пины с временем на карте показывают будущие события сегодня; в ленте — карточки «СКОРО» с заполненностью.
3. **«Куда ходят чаще всего рядом»** — карточки «ТОП» в ленте — площадки с самым большим числом check-ins за последний час.

### Что НЕ делаем в v1

- Отдельный экран фильтров (только полоса спорт-чипов под картой)
- Карта на полный экран — карта всегда занимает ~40% высоты, остальное — лента
- Push / уведомления о начале события
- Кастомные иконки на пинах — используем эмодзи спорта
- Heatmap-подкладка — только дискретные пины
- WebSocket / real-time — polling такой же, как на странице площадки (60s)
- Создание события / check-in с этой страницы — действия делаются на странице площадки
- Кластеризация пинов — в v1 без неё (площадок в одном городе ~десятки, не сотни)
- Поиск по карте — только селектор города
- Несколько городов в одной выборке — карта всегда вокруг одного центра

### Ключевые принятые решения

| Решение | Обоснование |
| --- | --- |
| Map-first компоновка (~40% карта, ~60% лента) | Карта даёт географическую интуицию, лента — детали |
| Имя страницы «Активність» / «Activity» | Покрывает и check-in (текущая активность), и событие (запланированная) |
| Доступ публичный, без логина | Discovery работает даже для незарегистрированных |
| Геолокация на старте, fallback Киев | Сценарий «рядом» требует координат, но не должен ломаться при отказе |
| «Топ» = check-ins за 60 мин | Самая простая, честная и понятная метрика |
| Клик по пину → сразу на страницу площадки | Промежуточная карточка дублирует ту, что уже есть |
| Единая лента смешанных карточек | Меньше переключения контекста, понятнее «что вокруг тебя» |
| Цветной левый бордер по типу карточки | Сразу читается: 🔴 live, 🟡 скоро, 🔵 топ |
| Сортировка ленты — близость × «горячесть» | Релевантность важнее хронологии |
| Полоса спорт-чипов фильтрует и карту, и ленту одновременно | Один контрол управляет обоими блоками |
| События тоже на карте (синие пины) | Запрошено в брейнсторминге — «активність + майбутнє одразу» |
| Без отдельной карточки превью при клике на пин | YAGNI — страница площадки уже даёт всю информацию |

## 5. Типы маркеров

| Тип | Источник данных | Визуал | Когда показывается |
| --- | --- | --- | --- |
| `live` | check-in за последние 60 мин | Красный пин-таблетка с эмодзи спорта и числом людей, лёгкая пульсация | На площадке есть активные check-ins |
| `event` | событие сегодня, в окне ±2 часа от текущего времени | Синий пин-таблетка с временем `18:00` | Запланировано на ближайшие часы |
| `inactive` | площадка без активности | Серая точка-кружок диаметром 12px | Площадка существует, но активности нет |

**Совмещение:** одна площадка может иметь и live, и event одновременно — рендерим оба пина с минимальным смещением (например, event чуть выше live).

**Цвет live-пина зависит от вида спорта?** Нет — все live красные, эмодзи отличает спорт. Это упрощает визуальный код «красное = live, синее = будущее, серое = пусто».

Клик по любому пину → `router.push(\`/sports-map/\${playgroundId}\`)`. Промежуточной карточки нет.

## 6. Сортировка и фильтрация ленты

Лента — единый массив `ActivityFeedItem`, отсортированный по релевантности.

### Формула сортировки

```ts
const score =
  liveBonus +           // +100 если есть active check-ins
  soonBonus +           // +50 если есть событие в ближайшие 2 часа
  topBonus +            // 60-минутный count * 5
  (10000 - distanceMeters) / 100  // ближе = выше
```

Идея: live всегда выше; внутри live — ближе и горячее выше; топ-площадка без live идёт ниже live, но выше неактивных.

### Фильтрация по спорту

Активный чип фильтрует одновременно карту и ленту:
- `live` карточка/маркер показывается, если у check-ins выбранный спорт
- `event` карточка/маркер — если у события выбранный спорт
- `top` карточка/маркер — если у площадки есть выбранный спорт в `playground.sports[]`

`Всі` (по умолчанию) — без фильтра.

### Лимит

Лента — без пагинации в v1. Показываем top-20 по скорингу, остальные обрезаем.

## 7. Карточки ленты — варианты

### Тип `live`
```
🔴 │ ⚽ 12 людей грають            [LIVE]   ›
   │ Парк Шевченка · футбол · 500м
```
- Левая полоска `border-l-3 border-red-500`
- Бейдж `LIVE` справа, красный фон
- Подпись: `{count} {людей грає|qty}` (через i18n plural)
- Расстояние: если геолокация есть → метры/км; иначе скрыть

### Тип `event` (СКОРО)
```
🟡 │ 📅 Футбол 5×5 за 30 хв        [СКОРО]  ›
   │ Парк Шевченка · 5/10 гравців · 18:00
```
- Левая полоска `border-l-3 border-amber-500`
- Бейдж `СКОРО`, янтарный фон
- Показывается, если событие в ближайшие **2 часа от текущего момента**
- События дальше (например, на вечер, но > 2ч) — НЕ в ленте `Активність`, они есть на странице площадки

### Тип `top`
```
🔵 │ 🔥 Олімпійський               [ТОП]    ›
   │ ★4.8 · 800м · 14 людей сьогодні
```
- Левая полоска `border-l-3 border-sky-500`
- Бейдж `ТОП`, голубой фон
- Показывается, если у площадки **нет** live и **нет** event-в-окне, но есть check-ins за календарные сутки > 0. Площадки без активности за сутки — НЕ в ленте (только серый пин на карте).
- Если ни у одной площадки в выборке нет суточных check-ins (новый район или ночь) — `top`-карточки отсутствуют, лента может быть пустая → показываем `empty`-стейт.
- Метрика "людей сьогодні" = count check-ins за календарные сутки на этой площадке.

Карточка кликается целиком → переход на страницу площадки.

## 8. Данные / API

### Что уже есть

| Файл | Используется как |
| --- | --- |
| `services/configs/playground.config.ts` | Список площадок с координатами, рейтингом, видами спорта |
| `services/configs/check-in.config.ts` | Активные check-ins (нужна выборка по времени) |
| `services/configs/event.config.ts` | События по площадке (нужна выборка по дате/радиусу) |
| `services/configs/sport.config.ts` | Список видов спорта для фильтра |

### Чего может не хватать

Скорее всего, существующие эндпойнты заточены под «дай мне всё по площадке id». Для страницы Активності нужны выборки по геолокации + времени.

Возможные требования к бэкенду (если ещё нет — добавить в API-спеку):

```
GET /api/playgrounds/activity?lat={}&lng={}&radius=3km
  → возвращает за один вызов:
    [
      {
        id, name, location, sports, rating, distance,
        activeCheckInsCount,    // count за последние 60 мин
        activeCheckInsBySport,  // { football: 12, basketball: 0, ... }
        upcomingEvents,         // события в окне сегодня ±2ч
        dailyCheckInsCount,     // count за календарные сутки
      },
      ...
    ]
```

**Альтернатива** — три раздельных вызова (`/playgrounds?near=`, `/check-ins?since=60m&near=`, `/events?date=today&near=`), агрегируем на клиенте. Так проще для v1, но 3 round-trip'а.

**Рекомендация:** v1 делаем тремя раздельными вызовами на готовых эндпойнтах, оборачиваем в `useActivityData()`. Если профайлинг покажет лаги — бэкенд добавляет агрегированный `/activity`.

### Polling

`useActivityData()` рефетчит все три источника **каждые 60s** (как уже устоявшаяся практика по спеке `playground-events-design.md`).

При смене города или координат — мгновенный рефетч.

## 9. Геолокация

`useGeolocation()` инкапсулирует логику:

```ts
type GeoState =
  | { status: 'pending' }
  | { status: 'granted'; lat: number; lng: number }
  | { status: 'denied'; lat: number; lng: number; reason: 'permission' | 'unavailable' | 'timeout' }

const DEFAULT_CITY = { name: 'Київ', lat: 50.4501, lng: 30.5234 }
```

Поведение:
1. На mount — `navigator.geolocation.getCurrentPosition()`.
2. Успех → `granted`, координаты идут в карту и API.
3. Отказ / ошибка → `denied`, координаты = `DEFAULT_CITY`.
4. В шапке селектор города (Київ / Харків / Одеса / Львів / Дніпро — список захардкожен в v1, потом из бэка). Смена города override'ит геолокацию.
5. В шапке кнопка «📍 Дозволити», если `status === 'denied' && reason === 'permission'` — повторно вызывает геолокацию.

Координаты пользователя в API не отправляются как «приватные» — только используются как параметр `near=lat,lng` для запроса близлежащих площадок.

## 10. Состояния страницы

| Состояние | Что показываем |
| --- | --- |
| `pending` (первая загрузка) | Скелетон карты (тёмный прямоугольник) + 3-5 скелетон-карточек ленты |
| `geo-pending` | Карта по дефолтным координатам (Київ), баннер «Запитуємо геолокацію…» |
| `geo-denied` | Карта по `DEFAULT_CITY`, в шапке кнопка «Дозволити геолокацію» |
| `empty` (нет ни check-ins, ни событий, ни площадок) | Карта пустая (только серые пины) + лента-empty: «У цьому районі поки тихо. Спробуй обрати інше місто або зайди пізніше» |
| `error` (API недоступен) | Тост-ошибка через `createToastInterceptor()` + кнопка «Спробувати знову» |

## 12. Производительность

- Карта рендерится один раз; обновляются только пины при новых данных.
- Polling 60s — приемлемо, ~3 запроса в минуту × 3 источника = 9 req/min на сессию. На бэке ставится cache 30s.
- Лента — максимум 20 элементов в DOM, без виртуализации.
- Геолокация запрашивается один раз на mount; если пользователь сменил координаты вручную — координаты считаем «выбранными», `navigator.geolocation` больше не дёргаем.

- **Unit** — `useActivityData` (мерджит три источника, сортирует), `useGeolocation` (state-machine), сортировочная формула.
